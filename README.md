# Dopasowanie nazwy szkoły

## 1. Założenia

Moduł przyjmuje nazwę szkoły wpisaną przez użytkownika w dowolnej formie (pełna nazwa, skrót, literówka, odmiana patrona, numer rzymski lub słowny, miasto w treści) i dopasowuje ją do konkretnej szkoły z listy. Wynikiem jest jeden z czterech statusów: `matched`, `ambiguous`, `suggestions`, `not_found` wraz z listą kandydatów i ich score. Całość jest wystawiona jako `GET /api/schools/match`.

## 2. Uruchomienie

Wymagania: Docker z Compose v2, `make`, `curl`.

```bash
make up        # build i start kontenerów: php (8.4-fpm), nginx, database (PostgreSQL 17)
make install   # composer install w kontenerze php
make db        # baza dev: create + migracje + fixtury (SchoolDataset)
make test      # PHPUnit; tests/bootstrap.php sam odtwarza bazę app_test
```

Porty i dane dostępowe można nadpisać w pliku `.env` w katalogu głównym (nie jest w repozytorium). Szablon znajduje się w `.env.dist`:

```bash
cp .env.dist .env
```

Bez pliku `.env` obowiązują domyślne: nginx `8080`, PostgreSQL `5432`, użytkownik/hasło/baza `app`.

### Zapytanie do API

```bash
make match NAME="II LO Gdańsk"
make match NAME="Staszic" CITY="Warszawa"
# lub bezpośrednio:
curl -sG "http://localhost:8080/api/schools/match" --data-urlencode "name=II LO Gdańsk"
```

Parametry: `name` (wymagany, 2–200 znaków), `city` (opcjonalny, max 100). Błąd walidacji → `422`.

### Komenda konsolowa

Ten sam przypadek użycia (handler i walidacja) dostępny z CLI; wynik w formie tabeli:

```bash

# lub bezpośrednio:
docker compose exec php bin/console app:school:match "II LO Gdańsk" [--city=Gdańsk]
```

## 3. Założenia i uproszczenia

- **Brak encji User** i przypisania użytkownika do szkoły – moduł tylko dopasowuje.
- **Dane z fixtury** (`SchoolDataset`) zamiast importu, np. z RSPO. Ten sam dataset zasila testy jednostkowe.
- **Mapowanie Doctrine atrybutami w klasach domenowych** zamiast XML. To świadomy kompromis: Domain „wie” o Doctrine (tylko metadane, bez zależności w logice), w zamian mniej plików i szybsza praca. Przy większym projekcie przeniósłbym mapowanie do XML w Infrastructure.
- **Stack**: projekt był przygotowany wcześniej na Symfony 8.1 (webapp), PHP 8.4-fpm + nginx i PostgreSQL 17, więc zostałem przy nim zamiast `symfony/skeleton` 7.4 + `php -S` + PG 16. Moduł nie używa niczego specyficznego dla tych wersji. Konsekwencje:
  - pakiet webapp dokłada Messengera z transportem Doctrine; tabela `messenger_messages` została usunięta z wygenerowanej migracji (Messenger jest poza zakresem), dlatego `doctrine:schema:validate` zgłasza tylko jej brak,
  - klucze główne to `GENERATED BY DEFAULT AS IDENTITY` (domyślna preferencja Doctrine dla PostgreSQL) zamiast `SERIAL` – semantycznie to samo,
  - w Symfony 8.1 `#[MapQueryString]` domyślnie zwraca 404 przy błędzie walidacji i pomija walidację przy pustym query stringu, dlatego kontroler ustawia jawnie `validationFailedStatusCode: 422` i `mapWhenEmpty: true`.
- **Etap fuzzy ładuje wszystkie szkoły z aliasami do pamięci** (jeden SELECT z JOIN FETCH). Dla tysięcy wpisów to milisekundy; przy skali całego RSPO potrzebny byłby prefiltr (patrz „Kierunki rozwoju”).
- **Normalizacja liczona przy zapisie** (`school_alias.normalized_name`). Zmiana reguł normalizatora wymaga przeliczenia kluczy wszystkich aliasów.
- `cityHint` w odpowiedzi to znormalizowana nazwa miasta (np. `gdansk`) – to wartość, którą faktycznie porównuje matcher.
- `normalized` w odpowiedzi to znormalizowane zapytanie przed usunięciem tokenu miasta (miasto widać osobno w `cityHint`).

## 4. Podejście

### Normalizacja (`NameNormalizer`)

Ten sam pipeline dla danych i zapytań:

1. małe litery, trim,
2. transliteracja polskich znaków (dalej wszystko jest ASCII, więc `levenshtein()` na bajtach jest poprawny),
3. interpunkcja → spacje,
4. frazy kanoniczne: `liceum (ogólnokształcące)` → `lo`, `zespół szkół` → `zs`, `tech` → `technikum`,
5. tokenizacja,
6. liczby: rzymskie (ścisły regex) i porządkowe słowne → arabskie; pojedyncze `i` jest liczbą tylko przed `lo/technikum/zs` lub po `nr/numer`,
7. stopwords (`im`, `nr`, `szkoła`, spójnik `i`, …),
8. prosty stemmer końcówek (`Konopnickiej`/`Konopnicka` → `konopnick`).

Stemmer bywa „zły językowo” (`zseii` → `zsei`, `marii` → `mari`), ale jest identyczny po obu stronach, a tylko spójność ma tu znaczenie.

Klucz wyszukiwania (`key()`) to **unikalne tokeny posortowane alfabetycznie**, więc exact match nie zależy od kolejności słów („Sienkiewicz LO” = „LO Sienkiewicza”).

### Kaskada dopasowania (`SchoolMatcher`)

0. **Przygotowanie** – normalizacja; wykrycie miasta (jawny parametr albo token pasujący do znanego miasta, Levenshtein ≤ 1 dla tokenów ≥ 5 znaków) i usunięcie go z zapytania; podpowiedź typu (`lo`/`technikum`).
1. **Exact** – zapytanie po indeksie `normalized_name`. Po filtrze miasta: 1 szkoła → `matched` (1.0), ≥ 2 → `ambiguous`; jeśli filtr usunął wszystko – przejście dalej (zadziała kara za miasto).
2. **Informatywność** – zapytanie musi mieć token niegeneryczny i niecyfrowy albo liczbę razem z typem (`5 lo`). `liceum`, `lo`, `5` → `not_found`.
3. **Fuzzy tokenowe** – dla każdego aliasu: zachłanne parowanie tokenów, podobieństwo `1 − d/max(len)` przy dopuszczalnym Levenshteinie (≤ 1 dla krótszego tokenu < 7 znaków, ≤ 2 dla dłuższych); liczby i tokeny < 4 znaków tylko dokładnie.
   ```
   M     = Σ waga · sim            (po sparowanych tokenach zapytania)
   Cq    = M / Σ wag zapytania
   Ck    = M / Σ wag klucza
   score = 0.7·Cq + 0.3·Ck
   ```
   Kary: inny typ × 0.5, inne miasto × 0.7. Score szkoły = maksimum po aliasach.
4. **Decyzja**:

| Warunek | Status | Kandydaci |
|---|---|---|
| top ≥ 0.85 i (brak drugiego lub top − drugi ≥ 0.1) | `matched` | 1 |
| top ≥ 0.85 i drugi bliżej niż 0.1 | `ambiguous` | wszyscy ≥ 0.85, max 5 |
| 0.6 ≤ top < 0.85 | `suggestions` | ≥ 0.6, max 3 |
| top < 0.6 lub brak | `not_found` | 0 |

Uzasadnienie:

- **Dlaczego nie czysty Levenshtein na całym stringu** – jest wrażliwy na kolejność słów („LO Sienkiewicza” vs „Sienkiewicz LO”) i uznaje „II LO” za bliskie „III LO” (odległość 1), co jest najgorszym możliwym błędem. Porównanie tokenowe rozwiązuje oba problemy, a Levenshtein zostaje tylko na poziomie pojedynczego tokenu (literówki).
- **Wagi tokenów generycznych** (`lo`, `technikum`, `zs` = 0.3) – te tokeny występują w połowie nazw, więc nie mogą same „wygrać” dopasowania; decyduje patron, numer, profil.
- **Asymetria Cq/Ck** – użytkownik zwykle wpisuje podzbiór nazwy oficjalnej („XIV LO im. Staszica” wobec pełnej nazwy z imieniem patrona). Ważniejsze jest, żeby wyjaśnić wszystko, co wpisał (Cq, 70%), niż pokryć cały klucz (Ck, 30%).
- **Twarda reguła numerów** – jeśli zapytanie i alias mają liczby, a zbiory są rozłączne, alias jest odrzucony. Numer szkoły jest identyfikatorem, nie „podobieństwem”.

## 5. Struktura modułu

```
app/src/School/
├── Domain/            # model i reguły: agregat School (+ SchoolAlias), enumy, interfejs repozytorium
│   └── Matching/      # normalizacja, VO NormalizedName, SchoolMatcher i obiekty wyniku
├── Application/       # przypadek użycia MatchSchool: DTO wejścia z walidacją, handler, DTO wyjścia (kontrakt API)
├── Infrastructure/    # implementacja repozytorium na Doctrine ORM (same zapytania, bez logiki)
│   └── Fixtures/      # SchoolDataset (jedyne źródło danych) + fixtura Doctrine
└── UI/                # cienki kontroler HTTP (query string → handler → JSON) i komenda konsolowa (argumenty → handler → tabela)
app/tests/
├── Double/            # InMemorySchoolRepository
├── Unit/              # NameNormalizerTest, SchoolMatcherTest (reguły na minimalnych danych), SchoolDatasetMatchingTest (przykłady ze specyfikacji na datasecie); w pamięci, bez bazy
└── Integration/       # MatchSchoolEndpointTest (WebTestCase), MatchSchoolCommandTest (CommandTester); baza app_test
```

- **Domain** nie zależy od pozostałych warstw (poza atrybutami Doctrine).
- **Application** tłumaczy wejście/wyjście na język domeny i nic więcej.
- **Infrastructure** tylko pobiera dane.
- **UI** tylko łączy HTTP i konsolę z handlerem.

## 6. Scenariusze brzegowe

- **Literówki** – `Mickiewcz` → Mickiewicz (0.9), `Stasic` → Staszic (0.86). Limit Levenshteina zależy od długości tokenu, żeby krótkie słowa nie „sklejały się” ze sobą.
- **Odmiana patronów** – stemmer sprowadza `Konopnickiej`, `Konopnicka`, `Słowackiego`, `Słowacki` do wspólnego rdzenia.
- **Numery rzymskie i słowne** – `III LO`, `Trzecie LO`, `3 LO` dają ten sam klucz `3 lo`. Numer różny od numeru szkoły odrzuca alias (reguła twarda).
- **Spójnik „i” kontra „I”** – `I LO` → `1 lo`, ale `Techniczne i Ogólnokształcące` → spójnik usunięty. Decyduje kontekst (następny `lo/technikum/zs` lub poprzedni `nr`).
- **Miasto w nazwie** – `2 LO Gdańsk` → miasto wykryte, usunięte z zapytania i użyte jako filtr/kara.
- **Wpisy nieinformatywne** – `liceum`, `LO`, `5` → `not_found` zamiast losowej szkoły.
- **Niejednoznaczność** – ten sam alias w dwóch miastach → `ambiguous` z listą kandydatów; podanie `city` rozstrzyga.
- **Konflikt typu** – `Technikum Mickiewicza` nie dopasuje się do liceum (kara × 0.5), zwraca `not_found`.

## 7. Kierunki rozwoju

- Kolejka moderacji: niedopasowane lub potwierdzone ręcznie wpisy stają się nowymi aliasami.
- Import z RSPO.

### Proste

- **Prefiltr kandydatów w bazie** – indeks trigramowy (`pg_trgm`, GIN) na `normalized_name` i wstępny wybór np. 200 najbliższych aliasów w SQL, a dopiero na nich obecny scoring tokenowy. Warunek konieczny przy skali całego RSPO, gdzie ładowanie wszystkich szkół do pamięci przestaje być akceptowalne.
- **Kalibracja na danych rzeczywistych** – logowanie zapytań z wynikiem i późniejszym wyborem użytkownika, zbudowanie z nich oznaczonego zbioru testowego i dobór progów oraz wag pod metryki (precision dla `matched`, recall dla `suggestions`). Zbiór służyłby też jako test regresyjny przy każdej zmianie normalizatora.
- **Wyszukiwanie semantyczne (`pgvector`)** – embedding liczony przy zapisie dla każdego aliasu (kolumna `vector` z indeksem HNSW) i dla zapytania; najbliższe wektory jako dodatkowe źródło kandydatów obok exact/fuzzy. Pomaga tam, gdzie reguły tekstowe nie widzą związku (opisowe wpisy, przestawione lub pominięte człony nazwy), a w przeciwieństwie do wywołania LLM jest deterministyczne i tanie w czasie zapytania. Kandydaci z tej ścieżki przechodzą przez te same twarde reguły (numer, typ, miasto) i trafiają najwyżej do `suggestions`, nigdy do `matched`.
